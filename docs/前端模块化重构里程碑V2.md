### 🔍 根本原因分析

#### 1. **双版本兼容 = 双版本债务**
```
V1 设计的 "渐进式重构"：
    index.html 大文件（稳定） ← 实际开发都用这个
          ↓ ?modular=1
    src/js/app.js 模块化（测试） ← 从来没人打开过
```

**结果：**
- 开发图方便，直接在 index.html 上加功能
- 模块化版本永远停留在4月30日的状态
- 相当于重构了个寂寞 😂

#### 2. **三个新模块全部堆在 index.html**
从4月30日到5月3日，3天时间新增了：
| 模块 | 大约行数 | 写在哪里？ |
|------|---------|-----------|
| 📰 文章库完整实现 | 600 行 | index.html |
| 📝 笔记库完整实现 | 800 行 | index.html |
| ✨ UX 统一优化 + 视觉配色 | 50 行 | index.html |

**净增：1450 行，直接翻倍还多！**

#### 3. **Setup 函数已经失控**

## 🎯 V2 重构核心原则

### ✊ 这次重构不搞"渐进式"了！

**原则 #1：不留后路，直接切断退路**
```
❌ V1：双版本兼容 → 结果都用旧版本
✅ V2：写完一个模块，删一个模块的代码
```

**原则 #2：先做垂直拆分，不是水平拆分**
```
❌ V1：按技术分层（API/Store/Utils）
✅ V2：按业务模块（论文/文章/笔记）
```

**原则 #3：拆一个，跑通一个**
> 拆完论文库，论文库要能正常跑
> 拆完文章库，文章库要能正常跑
> 绝对不搞"全部拆完再来联调"

## 💡 V2 重构的核心领悟

### 1. 为什么"渐进式"在小团队行不通？

**大公司渐进式重构可行：**
```
专人负责重构 → 专门的测试团队 → 强制切流量
```

**个人项目渐进式重构陷阱：**
```
开发就是同一个人 → 图方便直接改旧文件 → 新模块永远晾着
```

> ✅ **V2 结论：小项目重构就要大刀阔斧，直接删旧代码！**

### 2. 垂直拆分比水平拆分重要 10 倍

```
❌ 水平拆分（按技术分层）：
  API层 → Store层 → View层
  改一个功能要跳3个文件

✅ 垂直拆分（按业务模块）：
  论文库 → 文章库 → 笔记库
  改文章库就只打开 articleModule.js
```

> 绝大多数 Bug 都出在同一个业务模块内，垂直拆分才是真的解耦
